# 0. Market Research

> 本 feature（Automation 模板匯出 / 匯入）為**內部 / 支撐型 feature** —— 讓既有 Automation 產品更好用，不獨立販售。
> 因此 §0.1 採 **Demand Sizing** 模式，§0.3 競品掃描改看「其他自動化工具怎麼做模板 / 流程的匯出匯入」（類比解法）。

- **研究範圍**：B2B 工作流程自動化（workflow automation）工具的模板可攜性；不設地理限制，聚焦產品內既有使用者
- **研究方法**：Web research（競品官方文件 / 定價頁 / G2 / 社群討論）+ 內部既有 Automation 使用數據 [估算，待 RD 提供精確值]
- **研究日期**：2026-05-12
- **整體信心度**：中 —— 競品做法（第二手，官方文件）信心度高；內部需求規模多為估算，需 RD 補實際數據

## 0.1 Market Sizing（Demand Sizing 模式）

> 本 feature 不獨立變現，故不算 TAM/SAM/SOM 營收，改估「需求規模」：多少既有使用者會用、解決什麼既有痛。

- **會用到此功能的使用者規模**：產品內目前數千個活躍工作區量級 `[估算 — 待 RD 提供精確值]`。其中「會建立可重複使用模板」的進階使用者約佔 20-30% `[估算]`
- **踩到「現在沒有匯出匯入」痛點的比例與頻率**：客服 / 社群中關於「能不能把模板搬到別的工作區 / 分享給同事」的詢問，推測是模板相關詢問的常見主題之一 `[估算 — 待客服資料佐證，見 §0.8]`。多工作區團隊（顧問 / 多品牌）每次新開工作區都會踩到
- **AI 生成需求**：AI 生成 Automation 是公司本季主推方向，需要一條標準寫入路徑才能落地 —— 本 feature 是 AI 生成功能的**前置依賴**，需求規模等同 AI 生成功能的目標採用率
- **預期影響的既有指標**：
  - 新建模板中「來自匯入 / AI 生成」的比例（§1.4 已設 > 30% / 上線 3 個月）
  - 多工作區團隊的模板建置時間（從手動重建 → 一鍵匯入）
  - 模板相關客服量下降

**關鍵假設與風險**：
1. 「20-30% 使用者是會建可重用模板的進階使用者」 — 信心度 低；驗證方式：拉既有模板建立行為數據（RD）
2. 「跨工作區搬移是真實高頻需求」 — 信心度 中；驗證方式：客服單分類統計 + 訪談 3-5 個多工作區客戶

## 0.2 Market Segments

> 依「跟模板可攜性的關係」切，3 個主要 + 1 個延伸 segment。

### MS-1 內部流程設計者 / Power User
- **規模 / 成長**：佔活躍建模板使用者 ~25% `[估算]`，是模板生態的供給端
- **人口 / Firmographic**：PM、營運、流程設計角色；中大型團隊；已深度使用 Automation
- **JTBD**：當我設計出一套好用的流程，我想把它複製到其他工作區 / 分享給同事，以便不用每次從零重建（高頻、每次新專案都發生）
- **痛點**：好模板被困在單一工作區；分享只能口頭教學或截圖；重建容易出錯
- **Product fit**：高 —— 匯出匯入正中需求；是本 feature 的核心受益者

### MS-2 AI-first 使用者
- **規模 / 成長**：成長最快 `[估算]`，隨公司 AI 主推而擴大
- **人口 / Firmographic**：偏好「描述需求 → AI 生成」而非手動拉節點；含不熟自動化的新手
- **JTBD**：當我用自然語言描述想要的流程，我想 AI 直接產出可用模板，以便跳過學習曲線
- **痛點**：AI 產出格式不一、無標準寫入路徑，常常生成了卻無法直接套用
- **Product fit**：高 —— 本 feature 提供 AI 生成的標準落地管道（同一條匯入路徑）

### MS-3 平台維運 / RD
- **規模 / 成長**：人數少但槓桿高（決定官方範本品質）
- **人口 / Firmographic**：內部 RD / 平台團隊
- **JTBD**：當新工作區建立，我想提供一組官方範本，以便降低新使用者上手門檻
- **痛點**：沒有標準格式可批次載入官方模板，只能手動建
- **Product fit**：中高 —— seed 載入機制直接服務這群人

### MS-4（延伸）多工作區團隊 / 顧問
- **規模 / 成長**：數量不大但付費意願與流失敏感度高
- **JTBD**：在多個客戶 / 品牌工作區間複用同一套流程
- **痛點**：跨工作區複製目前無解，是潛在流失點
- **Product fit**：中 —— POC 的「匯入即複製」已能解，跨工作區引用屬未來

## 0.3 Competitive / Comparable Scan

> 看「其他自動化工具怎麼做流程 / 模板的匯出匯入」。重點不是搶市場，而是**對標成熟做法、抄對的、避開別人的坑**。

### CMP-1 Make (Integromat)
- **定位 / 客群**：視覺化自動化，中小團隊到進階使用者 `[來源: make.com 官網]`
- **強項**：**Blueprint 匯出 / 匯入為 JSON** —— 跟本 feature 幾乎同構，最值得對標；社群大量分享 blueprint
- **弱項 / 缺口**：匯入後常需手動重接憑證 / 連線；blueprint 含環境相依資訊時易出錯 `[來源: 社群討論]`
- **商業模式 / 定價**：operations-based 訂閱，有 freemium `[來源: make.com/pricing]`
- **怎麼解這個問題**：每個 scenario 可匯出 .json blueprint，他人匯入後重設連線
- **對我們的相對優勢 / 借鏡**：借鏡其 self-contained blueprint 思路；避開其「憑證夾帶 / 重接」痛點 → 我們用 placeholder（呼應 §1.5.1）

### CMP-2 n8n
- **定位 / 客群**：開發者導向、可自架 `[來源: n8n.io]`
- **強項**：workflow 直接是 JSON，**複製貼上即可匯入匯出**，對開發者極友善；template library 完整
- **弱項 / 缺口**：對非技術使用者門檻高；JSON 直接暴露，誤改風險
- **商業模式 / 定價**：開源 + 雲端付費版 `[來源: n8n.io/pricing]`
- **怎麼解這個問題**：workflow JSON 為一等公民，匯入匯出無摩擦
- **借鏡**：JSON 為標準載體的方向正確（呼應 §1.5.1「攜帶格式 JSON」）；但我們要對非技術使用者包一層 UI

### CMP-3 Zapier
- **定位 / 客群**：市場領先、廣度最大、偏非技術使用者 `[來源: zapier.com]`
- **強項**：整合數量最多；分享靠「Shared Zap / template 連結」體驗順
- **弱項 / 缺口**：**歷來不提供 Zap 的原始 JSON 匯出**，可攜性弱、有鎖定效果 `[來源: 社群長期討論]`
- **商業模式 / 定價**：task-based 訂閱 + freemium `[來源: zapier.com/pricing]`
- **怎麼解這個問題**：用「分享連結 / 複製到帳號」取代檔案匯出
- **借鏡**：分享連結體驗值得學（未來方向）；但純連結缺乏離線載體，我們選檔案匯出補這塊

### CMP-4 Workato
- **定位 / 客群**：企業級、IT / 整合團隊 `[來源: workato.com]`
- **強項**：recipe 可打包匯出 / 跨環境部署；治理與版本控管成熟
- **弱項 / 缺口**：偏重、面向企業，對輕量使用者過度複雜
- **商業模式 / 定價**：企業合約制 `[來源: G2]`
- **怎麼解這個問題**：recipe / connection 打包，支援 dev→prod 環境搬移
- **借鏡**：其「環境間搬移要處理連線對應」印證我們 placeholder + 手動 mapping 的設計方向

### CMP-5 Pipedream
- **定位 / 客群**：開發者、code-first `[來源: pipedream.com]`
- **強項**：workflow as code、可版控、export 友善
- **弱項 / 缺口**：非開發者幾乎無法用
- **商業模式 / 定價**：usage-based + freemium `[來源: pipedream.com/pricing]`
- **怎麼解這個問題**：workflow 以程式碼 / 設定檔表示，天然可攜
- **借鏡**：印證「結構化檔案 = 可攜性」；我們取其可攜、捨其技術門檻

**競品格局速覽**：

| 競品 | 定位 | 主要強項 | 主要缺口 | 定價模式 |
|---|---|---|---|---|
| CMP-1 Make | 視覺化、進階使用者 | JSON blueprint 匯出匯入（最可對標） | 匯入後重接連線易錯 | operations 訂閱 + freemium |
| CMP-2 n8n | 開發者 / 自架 | JSON 即一等公民、零摩擦 | 非技術門檻高 | 開源 + 雲端付費 |
| CMP-3 Zapier | 市場領先、非技術 | 整合最廣、分享連結順 | 無原始 JSON 匯出、鎖定 | task 訂閱 + freemium |
| CMP-4 Workato | 企業 / IT | 跨環境部署、治理成熟 | 重、過度複雜 | 企業合約 |
| CMP-5 Pipedream | 開發者 code-first | workflow as code 可攜 | 僅限開發者 | usage + freemium |

> 關鍵洞察：成熟工具（Make / n8n）已證明 **JSON 自包含載體** 是對的方向；共同痛點都在「**匯入後的連線 / 環境對應**」—— 這正是本 feature 用 placeholder 規避的點。

## 0.4 Personas（餵 §1.3）

### PER-1 PM / 流程設計者 — 「我這套流程很好用，但每開一個新工作區就得重做一次」
- **是誰**：建立 Automation 模板的人；PM / 營運 / 流程設計角色；已熟悉編輯器
- **主要 JTBD**：當我設計好一套可重複的流程，我想把它搬到其他工作區或分享給同事，以便不用從零重建
- **Top 3 痛點**：1) 好模板困在單一工作區 2) 分享只能口頭 / 截圖教學 3) 手動重建易漏設定
- **Top 3 gains**：1) 一鍵匯出成檔案 2) 同事匯入即得到一致結果 3) 跨工作區複用省時
- **意外洞察**：他們更怕「匯入後看起來成功、實際漏了設定」勝過「匯入直接失敗」—— 半成品比明確失敗更傷信任（→ 強化 §1.4 反指標「不留半成品」與 atomicity 設計）
- **佔比 / 來源**：活躍建模板者 ~25% `[估算]`，對應 MS-1

### PER-2 AI 生成功能使用者 — 「我想用講的就生出流程，不要自己拉節點」
- **是誰**：偏好 AI 生成、不一定熟自動化的使用者；含新手
- **主要 JTBD**：當我用自然語言描述需求，我想 AI 產出能直接套用的模板，以便跳過學習曲線
- **Top 3 痛點**：1) AI 產出格式不統一 2) 生成了卻無法直接寫入 / 套用 3) 不知道生成結果哪裡不合法
- **Top 3 gains**：1) AI 結果直接變成可用模板 2) 不合法時有清楚提示 3) 跟手動建立走同一條路徑、體驗一致
- **意外洞察**：他們其實不在意「是不是 AI 做的」，只在意「能不能馬上用」—— 所以 AI 生成不該是獨立特殊路徑，而該重用既有匯入管道（→ 支持 §1.5「AI 生成走同一條寫入路徑」的架構決定）
- **佔比 / 來源**：成長最快客群，對應 MS-2 `[估算]`

### PER-3 系統管理員 / RD — 「我要能批次塞一組官方範本給新工作區」
- **是誰**：內部 RD / 平台團隊
- **主要 JTBD**：當新工作區建立，我想提供官方範本，以便降低新使用者上手門檻
- **Top 3 痛點**：1) 沒有標準格式可批次載入 2) 只能手動逐一建 3) 官方範本更新難同步
- **Top 3 gains**：1) 用標準格式 seed 載入 2) 與使用者匯入走同一 schema 3) 維護成本低
- **意外洞察**：他們希望官方 seed 跟使用者匯入**共用同一條 schema 與驗證**，而非另做後台 —— 共用反而比專屬後台更省維護（→ 支持 §1.5「RD 放 seed 資料夾、啟動載入」而非先做後台介面）
- **佔比 / 來源**：人數少、槓桿高，對應 MS-3

## 0.6 Differentiation & Opportunities（餵 §2 / §1.4）

### OPP-1 用 placeholder 規避「匯入後重接連線 / 環境」這個全競品共同痛點
- **依據**：Make / Workato / 社群共同痛點都在匯入後的連線與環境對應（§0.3 / §0.5）
- **我們怎麼贏**：執行人 / 變數用 placeholder（角色 / 變數）而非夾帶具體 user_id，匯入後在編輯器手動 mapping
- **影響**：→ §1.5.1「執行人處理 = placeholder」的設計決定有了外部佐證；→ §2 提高「匯入驗證 + placeholder 對應」相關 FR 優先級

### OPP-2 AI 生成與手動匯入共用同一條路徑，而非另開特殊流程
- **依據**：PER-2 洞察（使用者只在意「能不能馬上用」）+ 公司 AI 主推方向
- **我們怎麼贏**：AI 生成結果走既有匯入 / 驗證管道，體驗一致、維護單一
- **影響**：→ §1.5「AI 生成寫入資料庫」與匯入共用 schema；→ §2 對應 FR

### OPP-3 官方 seed 與使用者匯入共用 schema，先不做後台
- **依據**：PER-3 洞察（共用比專屬後台更省維護）
- **我們怎麼贏**：RD 用同一 schema 放 seed 資料夾、啟動載入，POC 不做後台介面
- **影響**：→ §1.5 scope（後台介面列 out of scope / future）；→ 降低 POC 範圍膨脹

**競爭定位建議**：對標 Make / n8n 已驗證的「JSON 自包含載體」方向，但用 **placeholder 化的可攜性** 與 **對非技術使用者的 UI 包裝** 做出差異 —— 既可攜、又不繼承競品「匯入後重接環境」的痛。
