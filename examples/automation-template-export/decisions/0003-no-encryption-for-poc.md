# D-0003: POC 階段匯出檔案不做加密 / 簽章

- **Status**: Accepted
- **Date**: 2026-05-14
- **Affects**: §2.2 (NFR-5), §1.5.1
- **Supersedes**: —
- **Superseded by**: —

## Context

匯出檔案會在工作區之間、甚至未來跨組織流動。需要決定檔案是否加密（防讀取）或簽章（防竄改 / 驗證來源）。

POC 階段的前提：
- 內部試用為主，未對外開放（§9.1）
- 檔案已不含真實 user_id、workspace_id、DB 內部 ID（NFR-4, BR-3）
- 匯入端對所有檔案做完整 schema + 結構驗證（FR-3），不信任檔案來源

## Decision

POC 階段匯出檔案為純文字 JSON，不加密、不簽章（NFR-5）。涉及交易場景或跨組織分享時再重新評估。

## Rationale

- 檔案內已無機敏識別資料（NFR-4 保證），洩漏風險低
- 純文字 JSON 可讀、可手動編輯、易 debug，對 POC 的迭代速度價值高
- 安全邊界放在匯入端驗證（FR-3），而非檔案本身
- 加密 / 簽章帶來金鑰管理成本，POC 無對應的威脅模型

## Alternatives Considered

### A1: 簽章防竄改（檔案仍可讀）

**Pros**:
- 可驗證檔案未被修改、來源可信

**Cons**:
- 金鑰管理與簽章驗證的基礎建設成本
- 使用者手動編輯檔案（合理工作流）後簽章即失效，反而擋住正當使用

**Why rejected**: 「手動編輯匯出檔案」在 POC 是預期行為（例：修正後重新匯入），簽章與此衝突

### A2: 加密整份檔案

**Pros**:
- 內容完全不可讀，最高保密性

**Cons**:
- 失去可讀性與可編輯性，debug 困難
- 需要金鑰交換機制，跨工作區分享流程複雜化
- POC 無交易或機敏內容場景

**Why rejected**: 成本遠大於收益；NFR-4 已移除機敏識別資料

## Consequences

**Positive**:
- 檔案可讀、可手動修改、好 debug
- 匯出 / 匯入實作簡單，無金鑰基礎建設
- AI 生成（SF-3）與 seed 載入（SF-4）共用同一格式無額外處理

**Negative**:
- 檔案可被任意偽造或竄改 — schema 驗證能擋結構問題，但擋不了惡意內容語意
- 未來模板市集、跨組織分享（§1.5 Future）出現時，本決定需重新評估（可能 supersede）
